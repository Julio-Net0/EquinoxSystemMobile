Diagnóstico de Campo

O Desafio da Coleta em Usinas Fotovoltaicas Remotas

Por que sistemas tradicionais cloud-dependent falham nas operações solares?

📡 Desconexão Crítica
Usinas de geração distribuída (GD) ficam majoritariamente em zonas rurais e áreas isoladas onde o sinal 3G/4G é instável ou totalmente inexistente.

Impacto: Aplicativos comerciais que exigem handshake constante com APIs na nuvem sofrem timeout e impedem a execução da rota.
📝 Fragilidade Operacional
O fluxo alternativo manual — anotações em pranchetas de papel ou envio desestruturado de fotos em grupos de WhatsApp — gera retrabalho manual.

Impacto: Erros de digitação de kWh, perda de registros de faturamento e atraso de semanas para consolidar a geração mensal.
📍 Fraude e Falta de Auditoria
Inexistência de comprovação matemática de presença física do técnico na coordenada real da usina no exato instante da medição.

Impacto: Risco de lançamentos falsos feitos de dentro do escritório, violando normas de conformidade técnica e garantias de investidores.
Proposta de Valor

A Solução: Plataforma 100% Mobile & Offline-First

Resiliência matemática e operacional sem bloqueio de interface em campo

💾 SQLite Local como Single Source of Truth
Todas as leituras, usinas e ações são lidas e gravadas instantaneamente no banco de dados SQLite nativo do dispositivo.

A interface do usuário nunca aguarda requisições HTTP para responder: a resposta é imediata (sub-10ms), garantindo fluidez total mesmo no meio do pasto em Modo Avião.
🔄 Sincronização Delta Bidirecional
O aplicativo escuta o estado da rede via NetInfo. Ao restabelecer conectividade, o SyncManager faz o Push dos registros locais e o Pull apenas dos dados modificados remotamente após o último carimbo de data/hora (Delta Sync).
📸 Auditoria e Prova de Presença (Proof of Presence)
O formulário de medição exige a captura fotográfica do medidor físico compactada automaticamente no ato da foto, combinada com as coordenadas de GPS para auditoria de conformidade.
🏢 Arquitetura 100% Mobile Unificada
Elimina o custo e a complexidade de manter múltiplos front-ends (como painéis web separados). SuperAdmins, Admins e Técnicos usam o mesmo app móvel, com telas protegidas dinamicamente por RLS.

Especificação Textual dos Casos de Uso Chave

Pré-condições, fluxos principais, fluxos alternativos e pós-condições

⚡ UC07 — Registrar Nova Leitura
Ator: Técnico de Campo | Pré-condição: Logado com Usina selecionada.

Fluxo Principal:
  1. Técnico informa valor de medição em kWh;
  2. App dispara a câmera nativa e captura foto do medidor;
  3. App comprime a foto para JPEG 1080p (~300KB) no FileSystem;
  4. App coleta coordenadas GPS instantâneas;
  5. Gravação atômica: entidade criada no SQLite e enfileirada na action_queue.

Fluxos Alternativos:
  • Sem sinal de GPS: Alerta de satélite sem bloquear o salvamento;
  • Permissão Negada: Bloqueio com Fallback UI e atalho para Ajustes do SO.
🔄 UC12 — Sincronizar Dados (SyncManager)
Ator: Sistema (NetInfo) ou Disparo Manual | Pré-condição: Rede online.

Fluxo Principal:
  1. SyncManager lê itens pendentes da action_queue;
  2. Upload prioritário da foto comprimida para o Supabase Storage;
  3. Envio do payload da leitura ao PostgreSQL remoto;
  4. Remoção da fila local e atualização do status para Sincronizada;
  5. Execução do Pull Sync Delta via last_sync_timestamp.

Fluxos Alternativos:
  • Conflito Concorrente: Aplica Auto-Merge Last Write Wins silencioso;
  • Usina Inativada Remota: Marca status local como Rejeitada.

ADR 2.1

Identificadores Universais: Por que UUIDv4 no Domínio?

Eliminando o colapso de integridade relacional em sincronizações concorrentes

❌ O Desastre do Auto-Incremento (1, 2, 3...)
Se o SQLite local gerasse IDs sequenciais:
  • Técnico A em Goiás cria uma Leitura com ID 101 offline;
  • Técnico B na Bahia cria outra Leitura com ID 101 offline;
  • Ao sincronizarem com o Supabase ao mesmo tempo, ocorre colisão catastrófica de Chave Primária;
  • O banco exige remapeamento complexo de chaves estrangeiras, corrompendo referências locais.
✅ A Elegância Matemática do UUIDv4 no Domínio
O ID é gerado pela própria classe de Domínio antes de salvar no SQLite:
  • Espaço de 128 bits: probabilidade de colisão menor que 10-15;
  • Unicidade universal garantida mesmo com dezenas de técnicos offline;
  • Chaves estrangeiras locais já nascem apontando para o UUID final;
  • Zero necessidade de handshake prévio com a API do servidor remoto.
ADR 2.2

Action Queue & Motor de Sincronização Delta

Log transacional ordenado no cliente e tráfego delta econômico em redes instáveis

📋 A Tabela action_queue (Log Transacional)
Toda escrita offline grava uma linha atômica na tabela local:
id: UUIDv4
tipo_operacao: 'INSERT_LEITURA' | 'INSERT_USINA' | ...
payload_json: { ...dados completos serializados }
timestamp: Data/hora exata do evento local
tentativas: Contador de retries (máx 5)
Garante que mesmo se o app for finalizado pelo sistema operacional, nenhuma transação é esquecida.
⚡ Push Ordenado & Pull Delta Incremental
Push Sync: O SyncManager consome a fila respeitando a ordem cronológica dos eventos, garantindo consistência causal.

Pull Sync Delta: Em vez de baixar o banco inteiro da nuvem, o aplicativo consulta apenas:
SELECT * FROM usinas WHERE updated_at > :last_sync_timestamp;
Redução de 99% no consumo de banda móvel e processamento no dispositivo.
ADR 3.1

Otimização de Mídia: Compressão Agressiva 1080p

Redução de 95% do tamanho de arquivo sem sacrificar legibilidade técnica dos medidores

📸 Mídia Bruta da Câmera
Sensores modernos de smartphones geram arquivos de 8MB a 15MB por clique.

50 vistorias = ~600MB de espaço ocupado e timeout constante ao tentar subir via rede 3G instável.
⚙️ Pipeline de Processamento
Processamento imediato no CameraAdapter via expo-image-manipulator:
  • Redimensionamento proporcional máx: 1080p;
  • Compressão JPEG ajustada para 70-80%;
  • Execução assíncrona sem congelar a UI (< 800ms).
🎯 Resultado Otimizado
Arquivo final comprimido para ~300KB (redução de 95%).

Preserva nitidez total dos dígitos mecânicos e digitais para auditoria humana e OCR futuro, viabilizando upload instantâneo.
ADR 5.4

Prova de Presença (Proof of Presence) e GPS Consultivo

Auditoria de campo georreferenciada sem paralisar o trabalho sob condições adversas

📍 Auditoria Georreferenciada
No instante em que o técnico fotografa o medidor, o módulo de hardware aciona o expo-location para capturar as coordenadas de latitude e longitude.

Esses dados são salvos no Value Object CoordenadasGPS, comprovando aos investidores e gestores que o técnico esteve fisicamente nas imediações da unidade consumidora (UC).
🛡️ Política de Engenharia: GPS Consultivo
O Dilema: Em salas de comando blindadas ou galpões industriais com telhas de aço, o satélite GPS pode demorar ou não travar sinal.

A Decisão: O GPS atua para auditoria consultiva. O app alerta falta de sinal ou baixa precisão, mas nunca bloqueia o técnico de salvar a medição e seguir sua rota.
ADR 1.3 & 3.2

Segurança em Desconexão: Cold Start & Cofre de Sessão

Como garantir login offline seguro quando os tokens JWT corporativos já expiraram?

❄️ Cold Start Mandatório (Primeiro Acesso)
Após instalar o aplicativo, o primeiro login exige conectividade obrigatória com a internet:
  • Autentica no Supabase Auth e obtém o token JWT;
  • Solicita o cadastro de um PIN Local de 6 dígitos ou Biometria (FaceID/Digital);
  • Executa o Pull Sync inicial para popular o SQLite com as usinas da empresa.
🔐 Cofre em Hardware (expo-secure-store)
O PIN e as credenciais offline são gravados na Keystore (Android) e Keychain (iOS):
  • Em campo desconectado, o app valida o PIN localmente contra o cofre seguro;
  • Libera a UI e o SQLite mesmo se o token JWT de rede estiver expirado;
  • Ao voltar a ter internet, o SyncManager renova a sessão remota em background silenciosamente.

ADRs Críticos

ADRs Críticos: Last Write Wins & Storage Always First

Soluções arquiteturais desenhadas para proteção de integridade e experiência fluida

🤖 ADR 2.3 — Auto-Merge Last Write Wins
O Problema: Se dois técnicos enviarem leituras conflitantes para a mesma usina, como resolver?

Decisão: Abandonamos pop-ups na tela ("Qual versão manter?"). Técnicos leigos ficam confusos com merges manuais.

O sistema avalia o carimbo de medição (data_hora) e consolida a mais recente automaticamente, emitindo apenas uma notificação silenciosa de status.
🛡️ ADR 5.5 — Storage (Imagem) Always First
O Dilema de Ordem: Devemos subir o texto no PostgreSQL primeiro ou a foto no Storage primeiro?

Decisão: A foto é enviada obrigatoriamente antes do registro relacional.

Justificativa Fail-Safe: Se a conexão cair após subir a foto, temos no máximo uma imagem temporária órfã. Mas se o banco subisse primeiro, teríamos uma Leitura aprovada sem foto comprobatória, violando a regra de negócio.

ADR 5.7

Defesa em Duas Camadas: Zod vs. Invariantes de Domínio

Feedback instantâneo na UI combinado com blindagem hermética do núcleo de negócio

🎨 1ª Barreira: Apresentação (Zod + React Hook Form)
Objetivo: Experiência do usuário (UX) ágil e feedback visual na tela.
  • Impede cliques vazios nos botões de formulário;
  • Exibe mensagens amigáveis de validação tipada de campos;
  • Formata máscaras em tempo real (ex: CNPJ da empresa e decimais de kWh).
🛡️ 2ª Barreira: Invariantes do Domínio (DDD)
Objetivo: Garantia inegociável de sanidade e integridade dos dados.
  • Classes Leitura e Usina possuem invariantes em seus métodos;
  • Lançam exceções de domínio se valorKwh < 0 ou coordenadas forem inválidas;
  • Mesmo se a UI for burlada, o banco local e a fila nunca receberão registros corrompidos.
